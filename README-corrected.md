# Aegis H₂S — Passive H₂S Exposure-Dosimeter Wristband

**Smart India Hackathon 2026 — Problem Statement 26118 — Team Kaizen**
Official PS title: *Passive Colorimetric H₂S Exposure-Dosimeter Wristband with
AI-Based Quantitative Reading.* Our implementation of the "reading" step is a
**calibration model** (an explicit, swappable ΔE2000 → dose function), not a
trained machine-learning model — see [§3 Calibration model](#3-current-prototype-calibration-model)
below for why, and how a real regression fit would slot in later.

> **Read this before a demo or a judging round:** every dose number this app
> produces is generated by a placeholder calibration model. See
> [§6. What is simulated](#6-what-is-simulated) below before presenting it as
> anything more than that.

## 1. What Aegis H₂S is

Aegis H₂S is a **functional prototype** of a passive H₂S exposure-dosimeter
wristband, read with a smartphone: *"Passive H₂S exposure recording using a
colorimetric sensing strip, smartphone image analysis, CIEDE2000 colour
measurement and a calibration-ready dose model."* This repository is the
**software side only** — the physical wristband (Ag/Ag₂S strip, reference
patch, expiry indicator, ePTFE window, breakaway clasp) is described here in
UI/terminology but not manufactured in this repo.

It is **not** presented as a laboratory-validated occupational-exposure
instrument, a certified real-time H₂S alarm, or a medical device. See
[§8 Safety boundary](#8-safety-boundary).

## 2. Current prototype capabilities

- Live camera capture (`getUserMedia`) with an upload fallback, and a Demo
  Mode with ten deterministic presets for a repeatable walkthrough.
- Real pixel-level image processing: quality gates, layout-based region
  detection, reference-patch correction, RGB → XYZ → CIE Lab, CIEDE2000.
- A prototype (simulated) calibration model that turns ΔE2000 into a dose
  estimate with an uncertainty band and a confidence label.
- Worker, wristband and shift management, with a wristband lifecycle
  (Available → Assigned → Active → Expiring Soon → Expired → Retired).
- Role-based login (Safety Officer / Supervisor / Worker) with role-specific scan permissions.
  Safety Officers can verify wristband QR identities; Supervisors and Workers can perform
  the optical scan of the reactive strip, reference patch and expiry indicator.
- Local-only storage (IndexedDB), history with charts, and CSV/JSON export.

## 5. Prototype calibration model

The active model (`DEMO_CALIBRATION_PARAMS` in `services/calibrationModel.ts`)
is an exponential-saturation curve, `ΔE(dose) = ΔEmax·(1 − e^(−dose/D50))`,
with illustrative parameters. It is called a **prototype / calibration-ready
model** in the UI, never a "lab-calibrated model" — see §6 for the full
distinction. It implements a small `CalibrationModel` interface
(`forward()` / `invert()`) so a future lab-derived model is a drop-in
replacement via `setActiveModel()`, with no UI or storage changes required.

## 6. What is simulated

No laboratory H₂S calibration data exists yet for this project. Rather than
fabricate results, the app makes the simulation boundary explicit and
structural:

- **Everything upstream of the calibration model is real measurement code.**
  A blurry photo really does fail the sharpness check; a genuinely tarnished
  strip really does produce a larger ΔE2000 than a fresh one.
- **The calibration model — the one function that turns ΔE2000 into a dose
  number — is a labelled placeholder.** It implements a plausible
  exponential-saturation curve (`ΔE(dose) = ΔEmax·(1 − e^(−dose/D50))`) with
  illustrative parameters, not measured ones.
- Every dose result the UI shows carries **"SIMULATED RESULT — LAB
  CALIBRATION PENDING"** and every `DoseEstimate` object has
  `isSimulated: true` baked in — this is not a cosmetic label that can be
  forgotten, it's part of the data shape.
- The **Calibration model is a swap point**: `services/calibrationModel.ts`
  defines a `CalibrationModel` interface (`forward()` / `invert()`). A future
  regression fit to real chamber data becomes a second implementation of
  that interface, registered via `setActiveModel()`. No UI code, no storage
  code, and no other service needs to change.
- The **Calibration / Admin page** exists specifically to receive that real
  data later (`CalibrationSample` records — known concentration, duration,
  Lab reading, environment, batch, device). Until then it's seeded with a
  clearly-flagged synthetic dataset (`isDemo: true` on every row, labelled
  **"DEMO CALIBRATION DATA"** in the UI).
- Two more placeholder assumptions worth knowing about, both isolated in
  `src/data/constants.ts`: the "pristine silver" and "expected reference
  patch" starting colours are engineering estimates, not spectrophotometer
  readings of the actual physical materials. Swapping them for measured
  values needs no other code changes.
- The expiry-dot classification (`services/imageProcessing/expiryDetection.ts`)
  uses a placeholder lightness threshold pending characterisation of the
  real expiry ink — the *mechanism* (sample → classify → gate the
  quantitative result) is real and demonstrable even though the exact cut
  points are provisional.

If you take one thing from this section: **the math is real, the physical
constants feeding it are not yet.**

The current ΔE2000 → dose mapping uses illustrative/demo calibration
parameters and is **not laboratory validated.**

## 7. What requires laboratory validation

- Controlled H₂S chamber calibration (known-concentration, known-duration exposures)
- A validated ΔE2000 → ppm·h relationship, fit to that chamber data
- Multi-condition temperature/RH calibration — fields for this already exist on every
  `CalibrationSample` (see `types/index.ts`), but no compensation is applied yet
- Statistically validated confidence intervals (today's uncertainty band is a simple
  integrity-scaled heuristic, not a propagated-error model from measured noise statistics)
- Field / industrial pilot testing
- Occupational-deployment validation and any regulatory sign-off

## 8. Safety boundary

> Aegis H₂S is a passive exposure-recording prototype. It is not a certified
> real-time H₂S alarm, medical device, or replacement for PPE, site SOPs or
> certified safety monitoring. It complements — not replaces — certified H₂S
> alarms, PPE and site SOPs.

This wording is shown in-app on the Science page, the Settings/About page and
(in short form) on every dose-result screen.

## 9. Offline-first architecture

Scan, analyse and store are all local: every pipeline step (image capture,
quality checks, region detection, colour science, the calibration model,
measurement-integrity scoring) runs on-device, and results are written to
IndexedDB with no network call. Sync/export is deliberately a separate,
later step — CSV and JSON export exist today; a backend sync is future work
(see the Architecture page's dashed "future layer"). No unnecessary backend
is required to use the app.

## 10. Running the application

```bash
npm install
npm run dev        # http://localhost:5173, camera access needs HTTPS or localhost
```

```bash
npm run build       # production build to dist/
npm run preview     # serve the production build locally
npm run test:pipeline   # run the pixel-processing pipeline self-test (Node, no browser)
```

Camera access requires either `localhost` (works automatically) or HTTPS —
browsers block `getUserMedia` on plain HTTP from a LAN IP. If you need to
demo from a phone on the same network, use a tunnel (e.g. `ngrok`) or serve
over HTTPS.

## Architecture

```
src/
├── types/index.ts              Domain types shared by pipeline, storage and UI
├── services/
│   ├── colorScience/           sRGB→XYZ→Lab, CIEDE2000 (validated, see below)
│   ├── imageProcessing/
│   │   ├── regionSampling.ts   Layout-proportion ROI detection + manual ROI fallback
│   │   ├── imageQuality.ts     Blur/brightness/glare/clipping/framing validation
│   │   ├── colorCorrection.ts  Reference-patch based lighting correction
│   │   ├── expiryDetection.ts  Expiry-dot classification
│   │   └── demoFrameGenerator.ts  Draws real synthetic frames for Demo Mode
│   ├── calibrationModel.ts     The one swappable dose-model file (see above)
│   ├── measurementIntegrity.ts Prototype 0-100 quality score + breakdown
│   ├── scanPipeline.ts         Orchestrates the above into one Measurement
│   ├── storage/                StorageService interface + IndexedDB implementation
│   └── exportService.ts        CSV / JSON export
├── data/                       Constants, demo seed data, demo calibration dataset, demo presets
├── context/AppContext.tsx      Storage init, demo seeding, active worker/shift state
├── hooks/useCamera.ts          getUserMedia wrapper with graceful fallback
├── components/                 UI, grouped by feature (scan, result, workers, charts, layout, common)
└── pages/                      One file per route
```

**Why this shape:** the brief specifically asks for a calibration model that
can be replaced "without redesigning the application" and storage that can
move off IndexedDB later. Both are satisfied by keeping a narrow interface
(`CalibrationModel`, `StorageService`) between the UI and the thing that
might change, rather than letting either leak into components.

### A deliberate departure from the requested stack: no OpenCV.js

OpenCV.js is an ~8 MB WASM payload. None of the required operations here —
region-mean colour sampling, Laplacian-variance blur detection, histogram
brightness/glare checks — need a full computer-vision library, and pulling
one in works against the "offline-first, runs well on a phone" goal. All
image processing is done with the Canvas 2D API and plain TypeScript math
instead. It's still real, pixel-level processing; it's just not OpenCV.

### Region detection approach

Per the brief's explicit permission to avoid ML object detection, region
detection uses **known layout proportions**: the person aligns the physical
wristband inside an on-screen guide box (draggable/resizable — this is also
the "manual ROI fallback" required when automatic confidence is low), and
the sensing/reference/expiry sub-rectangles are located as fixed fractions
of that box. Two additional real checks catch a badly-framed or non-wristband
capture that fixed proportions alone can't: a corner-vs-interior structural
contrast measure, and an inter-region colour-distinctness check.

## Demo Mode

Demo Mode does not fabricate a dose number directly — it fabricates a
plausible **photograph** (a real `HTMLCanvasElement` with real pixels: a
genuine `blur()` filter pass for the blurry preset, a real radial gradient
for glare, real per-pixel noise for the obscured reference, etc.) and runs
that image through the *exact same* pipeline a live capture would use. "Demo
mode" and "mechanism demonstration only" are shown on-screen because the
input photo is synthetic — the processing is not.

Ten presets are included: clean/unexposed, low/moderate/high simulated
exposure, expired badge, blurry scan, excessive glare, poor lighting,
missing reference, and invalid wristband — covering both the happy path and
every rejection path described in the brief (§10, §11).

## Suggested demo flow (~60–90s)

1. Supervisor/Worker Dashboard → confirm active worker/shift
2. Supervisor/Worker Scan → Live camera (or Demo Mode for a controlled run) → capture

Safety Officer flow: Dashboard → Verify Wristband QR → scan/verify the printed Band ID.
Safety Officers do not access the optical strip/reference/expiry measurement workflow.
3. Confirm alignment → Run Analysis
4. Watch the six-stage processing animation
5. Review the result: dose, range, confidence, integrity score, expand
   "Technical Analysis" to show the underlying Lab/ΔE2000 numbers
6. Save Reading → open Worker History → see the point land on the trend chart
7. Second pass: Demo Mode → "Blurry scan" or "Excessive glare" →
   **Measurement Rejected**, with the specific reason shown

## 11. Testing / building

- `npm run test:pipeline` runs the real detection → quality → correction →
  calibration → integrity pipeline against synthetic pixel buffers for all
  ten demo scenarios, entirely in Node (no browser needed). It also asserts
  the demo review-step guide box maps back exactly to the region a demo
  frame's patches were drawn into (an integration bug this test was written
  to catch).
- The CIEDE2000 implementation was checked against the standard Sharma, Wu
  & Dalal (2005) reference test pairs and matches to 4 decimal places.
- `npm run build` produces a clean, route-code-split production bundle.

## Known limitations / next steps

- The reference-based lighting correction is a first-order additive Lab
  shift, not a full von Kries or per-channel gain model — a reasonable
  starting point, not a claim that lighting variability is solved.
- Expiry-dot thresholds and the two baseline colours in `data/constants.ts`
  are engineering placeholders pending real material characterisation.
- The manual ROI fallback is a single adjustable box (not three
  independently draggable regions) — chosen for reliability within the
  prototype timeline; the sub-region proportions inside it match the
  physical wristband layout.
- No automated UI/visual test suite; correctness was verified at the
  TypeScript/pipeline level (`tsc`, `npm run test:pipeline`, `npm run
  build`) rather than with a browser-automation screenshot pass.

### Troubleshooting: white screen / stale app
If you ran an older copy of this project on the same address, the browser may hold an old
service worker + cache. This version removes it automatically in dev and shows an error
screen with a **Reset app cache & sign out** button instead of a blank page. Manual fix:
DevTools > Application > Service Workers > Unregister, then Clear site data.
Demo logins (password `demo1234`): `officer.demo`, `supervisor.demo`, `worker.demo`.

### Troubleshooting: everything is blank (no workers / history / calibration rows)
Caused by an old `h2s-dosimeter` IndexedDB left by an earlier copy of the project.
The database schema is now versioned (v2) and repaired automatically on startup; each data set
is seeded independently, and a **Load demo data** banner appears if anything can't be loaded.
Manual reset: DevTools > Application > Storage > Clear site data.
